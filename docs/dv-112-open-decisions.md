# DV-112 — 팀 결정이 필요한 안건

사업자등록증 검증(DV-112)을 구현하면서, **dev의 설계 문서(`team-creation-api-spec.md`)에 없던 것들이
코드에 들어갔다.** 설계 문서를 정본으로 삼기로 한 이상, 이것들은 "구현했으니 끝"이 아니라 팀이
스펙으로 받아들일지 결정해야 하는 항목이다.

이 문서는 그 목록이다. 각 항목마다 **무엇이 들어갔고 / 왜 들어갔고 / 무엇을 잃는지**를 적었다.
결정이 나면 해당 내용을 설계 문서에 반영하고 이 문서에서 지운다.

> 코드는 지금 그대로 두었다. 결정 전에 지우지도, 정당화하지도 않는다.

## 1. 광고업 심사 신설 — 가장 큰 안건

### 무엇이 들어갔나

**"광고업 사업자만 팀을 만들 수 있다"**는 규칙이 생겼다. 업태·종목을 OCR로 읽어 광고 관련 키워드와
대조하고, 광고업이 아니라고 판정되면 **팀 생성을 거부한다**(`400 BUSINESS_400_105~107`).

관련 산출물: `AdvertisingClassifier`, 판정 규칙 5~7번, `V6` 마이그레이션(`business_item` 컬럼),
`docs/server-verification-spec.md`(270줄), 업로드 토큰 payload 확장, OCR Lambda 계약 변경.

### 왜 안건인가

dev 설계 문서는 정반대를 명시했다.

> OCR도 이 중 문서에 실제로 인쇄돼 있는 4개(사업자명/대표자명/사업자등록번호/개업일자)만 추출하면 된다.
> **업태·사업장 소재지는 이번 화면에 아예 없으므로 OCR 대상이 아니다.**

즉 광고업 심사는 **설계에 없던 제품 요구사항**이다. 구현 과정에서 생긴 것이지 합의된 것이 아니다.

### 무엇을 잃는가 (이게 핵심)

업태·종목은 **화면에 입력란이 없다.** 사용자가 고칠 수 있게 하면 음식점업 사업자가 "광고대행"으로
바꿔 스스로를 승인시킬 수 있어서, 일부러 폼에서 빼고 OCR 원본을 서명 토큰으로만 나르기 때문이다.

그 대가로 **OCR이 업태·종목을 잘못 읽으면 사용자에게 탈출구가 없다.**

- 정상적인 광고대행사인데 종목이 "마케팅"으로만 잡히면 → `400`, 팀 생성 불가
- OCR이 업태·종목 칸을 못 읽으면 → `400`, 팀 생성 불가
- 사용자가 할 수 있는 건 **재업로드뿐**이고, 재업로드는 24시간 10회 한도를 소모한다

보안(위조 방지)과 가입 성공률을 맞바꾼 설계다. **기획·프론트와 합의가 필요하다.**

### 결정할 것

- [ ] 광고업 심사를 제품 요구사항으로 확정할 것인가?
- [ ] 확정한다면, OCR 오독 시 사용자 구제 경로를 어떻게 줄 것인가?
      (예: 수동 검토 대기열, 고객센터 문의, 업태를 폼에 노출하되 OCR 값과 다르면 `review_required`)
- [ ] 확정하지 않는다면, 관련 코드를 들어내고 dev 설계대로 4필드 OCR로 되돌린다.

## 2. OCR Lambda 계약 변경 — 배포 순서 주의 (크로스 레포)

Lambda는 별도 레포(`biz-eligibility`)에서 배포한다. **계약이 바뀌었다.**

| | dev 설계 | 현재 구현 |
|---|---|---|
| 요청 | `{ bucket, key }` | `{ action: "ocr", bucket, key }` |
| 응답 | 4필드 | **6필드** (`+businessType`, `+businessItem`) |

**Lambda가 백엔드보다 먼저 배포되지 않으면 조용히 망가진다.** 옛 Lambda가 업태·종목을 안 돌려주면
분류가 `unknown`이 되고 → 판정 규칙 5번 → **모든 팀 생성이 `400`으로 실패한다.** OCR 실패는 업로드
단계에서는 흡수되지만 팀 생성 단계에서는 치명적이다.

이 항목은 1번 안건에 종속된다 — 광고업 심사를 접으면 Lambda 계약도 원래대로 돌아간다.

### 결정할 것

- [ ] (1번이 확정될 경우) Lambda 레포 배포를 백엔드보다 먼저 나가도록 조율

## 3. 설계 문서에 없는 API·응답 코드

전부 dev 설계 문서에 **한 번도 등장하지 않는다.** 구현하면서 필요해서 넣은 것들이다.

| 항목 | 코드 | 왜 넣었나 | 빼면 무슨 일이 생기나 |
|---|---|---|---|
| 사업자등록증 재제출 API | `POST /teams/{teamId}/business-registration` | 반려·검토필요 판정을 받은 팀이 문서를 다시 낼 경로가 없었다 | 한 번 반려된 팀은 영원히 복구 불가 |
| 업로드 횟수 제한 | `429 BUSINESS_429_001` (24h / 10회) | 업로드 1회 = OCR 1회 = 과금. 인증만으로 무제한 호출 가능했다 | 로그인한 사용자 하나가 OCR 비용을 계속 태울 수 있다 |
| 사용자당 팀 1개 강제 | `409 BUSINESS_409_002` | `UserMeResponse`가 `teamId`를 하나만 반환한다 | 두 번째 팀이 만들어지되 **사용자가 접근할 수 없는 유령 팀**이 된다 |
| 승인 후 재제출 차단 | `409 BUSINESS_409_001` | `team_id` UNIQUE라 재제출이 UPDATE로 동작 | 이미 `APPROVED`인 팀이 잘못된 문서를 올리면 승인 상태가 `REJECTED`로 덮인다 |
| 사업자등록증은 OWNER만 | `403 BUSINESS_403_002` | ERD 4절 "권한 기준"에 근거 | 일반 멤버가 팀의 사업자 정보를 바꿀 수 있다 |

넷 다 "없으면 실제 사고가 나는" 방어라서, 저는 **문서에 추가해 스펙으로 승격**하는 쪽을 권한다.
다만 설계 문서를 정본으로 삼기로 한 원칙의 예외이므로 팀 확인을 받는다.

### 결정할 것

- [ ] 위 5개를 스펙으로 승격하고 설계 문서에 반영할 것인가? (권장)
- [ ] 승격하지 않는다면 어느 것을 코드에서 뺄 것인가?

### 알려진 한계 (승격한다면 함께 결정)

업로드 횟수 제한은 **인스턴스 메모리 기반**이라 스케일 아웃하면 서버 대수 × 10회가 된다.
지금은 EC2 1대라 문제없지만, 늘리려면 Redis 등 공유 저장소가 필요하다.

## 4. 국세청 API 실패: `500` vs `502`

**현재는 문서대로 `500`(`BUSINESS_500_004`)이다.** 구현이 한때 `502`였으나 문서를 정본으로 삼아 되돌렸다.

의미상으로는 `502 Bad Gateway`가 더 정확하다 — 우리 서버 결함이 아니라 상위 의존 서비스(국세청)의
실패이기 때문이다. 프론트가 5xx를 어떻게 다루는지(자동 재시도 여부)에 따라 실익이 갈린다.

### 결정할 것

- [ ] `502`로 개정할 것인가? 개정한다면 설계 문서를 먼저 고치고 코드를 따라가게 한다.

## 5. "팀 없음"을 404로 할까 403으로 할까 — 도메인 내 정책 충돌

같은 `team` 도메인 안에서 **정반대 정책이 공존한다.**

| | 백엔드 A (초대코드·팀원 관리, DV-113/120) | 백엔드 B (사업자등록증, DV-112) |
|---|---|---|
| 팀이 없을 때 | `404 TEAM_404_001` | `403` (404와 구분하지 않음) |
| 근거 | 설계 문서 6절이 404를 명시 | 팀 존재 여부가 외부로 새는 것을 막으려고 의도적으로 통일 |

DV-112 쪽 주석에는 이렇게 적혀 있다 — *"구분해서 404/403으로 나눠 응답하면 팀의 존재 여부가 외부에
새어 나간다."* 그런데 백엔드 A는 바로 그 404를 쓴다. 프론트 입장에서도 같은 도메인의 API가 서로 다르게
동작하는 셈이다.

(에러 코드 접두사는 `TEAM_`/`BUSINESS_`로 갈려 있어 충돌은 없다.)

## 8. 백엔드 A에 넘길 버그 2건 (DV-113 산출물)

`LocalDashboardMockDataInitializer` 관련이다. DV-112 쪽에서 우회했지만 근본 원인은 그쪽에 있다.

1. **주석과 코드가 다르다.** `application-local.yml` 주석은 "기본값은 꺼둔다"인데 실제 기본값은
   `true`(`LOCAL_DASHBOARD_MOCK_DATA_ENABLED:true`)다.
2. **`Clock`을 목킹하는 모든 테스트의 컨텍스트를 깨뜨린다.** 이 초기화기가 `ApplicationRunner`라
   컨텍스트 기동 시점에 `LocalDateTime.now(clock)`을 호출하는데, 시간을 고정하려고 `Clock`을
   `@MockitoBean`으로 바꾼 테스트에서는 `getZone()`이 `null`이라 NPE로 컨텍스트가 뜨지 못한다.
   (DV-112는 해당 테스트에서 초기화기를 끄는 것으로 우회했다.)
